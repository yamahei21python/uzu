# lalamo 0.8B QAD (KL蒸留) 性能遅延・Loss非改善の原因調査報告書

## 1. 実測データとエグゼクティブサマリ
0.8B QAD (KL蒸留) において、**50 step で約82分 (98.4秒/step)** を要し、loss も悪化する事象を調査した【実測】。

### 表1: 50 step 実測損失ログの推移【実測】
| step | 実測 KL | 状態・フェーズ | 観測動向【実測】 |
|---:|---:|:---|:---|
| 1 | 0.155950 | 初期状態 (YAQA直後) | 最適ベイスン内の極小値 |
| 5 | 0.769761 | Muon 初期更新 | 急激な悪化 (+0.61) |
| 10 | 0.742093 | チェックポイント #1 | 高止まり・振動 |
| 20 | 1.290452 | チェックポイント #2 | 発散進行 (1.2突破) |
| 30 | 0.838976 | チェックポイント #3 | チャンク依存の一時低下 |
| 40 | 1.563061 | チェックポイント #4 | 再度の大幅悪化 |
| 50 | 1.741509 | チェックポイント #5 | 最大値 (初期比11.2倍) |

**最有力原因3点**:
1. **T4 の BF16 非対応と Muon NS 演算負荷【推定】**: Turing T4 は BF16 Tensor Core を欠き FP32 エミュレーションで動作。112 行列の Newton-Schulz 5反復が重なり遅延を主導。
2. **QAD に対する Muon の不適と過大学習率【推定】**: YAQA 調整済み重みに対し `muon_lr=1e-3` の直交更新が過大。AdamW (1e-4) スケールとの乖離 (Scale Lag) で量子化が破綻。
3. **極小バッチ (batch=1, seq=128) の STE ノイズ増幅【推定】**: 128 トークンの STE 勾配ノイズが Muon の特異値均一化により全方向に増幅。

## 3. Loss非改善と初期値（step1）異常の機序
- **step 1 (0.156) の低さ**: YAQA キャリブレーション (`scripts/yaqa_calibration.py:45`) 直後の最適状態を直接反映【引用】。
- **step 5 以降の急悪化**: 勾配更新で重みが直交回転され、INT4 グリッドから逸脱。

### 表3: Loss 悪化要因の感度マトリクス【推定】
| 要因 | 寄与度 | メカニズム【推定】 |
|:---|:---:|:---|
| Muon 直交更新 (`1e-3`) | **極大** | 特異値一様正規化により最適ベイスンを強制離脱 |
| Scale Lag (追従遅延) | **大** | scales/zeros (AdamW 1e-4) が重み変動に追従不能 |
| STE 勾配ノイズ | **大** | batch=1 (128トークン) の高分散を特異値直交化が増幅 |
| ランダムチャンク分散 | **中** | 毎 step 難易度の異なるテキストを評価し振動 |
| 温度 T=1.0 鋭角化 | **中** | 語彙 128k に対し確率が鋭角化し勾配スパイク |

## 4. 最適化アルゴリズムの妥当性評価（Muon vs 代替手法）
Muon は事前学習向きであり、QAD の微細蒸留には純粋 AdamW が適する。

### 表4: オプティマイザ特性比較【推定】
| 手法 | メモリ | T4 負荷 | QAD 適合性 | 特徴【推定】 |
|:---|:---:|:---:|:---:|:---|
| **Muon + AdamW** (現状) | 中 | 高 (1680 matmuls) | **不適 (×)** | 【実測】設定。ノイズ増幅と重み発散を招く。 |
| **純粋 AdamW** (推奨) | 高 | **極小 (Elementwise)** | **最適 (◎)** | 微小 lr (2e-5) でベイスン内を安定微調整。 |
| **Lion** | **極小** | 極小 (Sign更新) | **良好 (◯)** | メモリ節約だが Sign が STE ノイズと干渉。 |
| **Adafactor** | 低 | 小 | **良好 (◯)** | 長期向き。50 step では分散推定が未収束。 |
| **SOAP** | 極大 | 極大 (SVD頻発) | **不適 (×)** | 固有空間計算が T4 で破綻。 |

## 5. 並列方式（2×T4 Replicated）と Checkpoint
- **Replicated の冗長性**: `batch=1` では 2 台の T4 で同一計算が重複し PCIe 3.0 通信遅延のみ加算【推定】。TP=2 は `research/qad_tp_optimizer.md:34` の通り Muon で `ShardingTypeError` 発生【引用】。
- **Orbax 停止時間**: `PyTreeCheckpointer` の 6〜8GB 保存が step 10,20,.. で発生。

### 表5: 並列構成・保存設定の比較【推定】
| 構成 | 有効スループット | 通信負荷 | 評価【推定】 |
|:---|:---:|:---:|:---|
| **2×T4 Replicated** (現状) | 冗長 (非効率) | PCIe All-Reduce 大 | 【実測】非推奨 |
| **1×T4 単体** (推奨) | **100% 活用** | **通信ゼロ** | 最速・安定 |
| **save-every 10** (現状) | I/O 停止 5回 | ディスク負荷大 | 【実測】82分の7分占有 |
| **save-every 0** (推奨) | **I/O 停止ゼロ** | ディスク負荷なし | 診断実行に最適 |

## 6. データパイプラインと評価基準の是正
- **トークン数不足**: `seq=128, batch=1` は 128 トークンに過ぎず STE には致命的。
- **固定 Val Loss 導入**: 8 チャンクの固定検証セットで真の汎化損失を評価。
- **温度緩和**: $T=1.0 \to 1.5$ でロジットを軟化させテールノイズを遮断。

## 9. 失敗モードと防護策
1. **Scale Collapse**: `scale_min=1e-5` の下限保護と `optax.clip` を適用【引用】。
2. **STE Gradient Explosion**: `optax.clip_by_global_norm(1.0)` を必須適用。
3. **Log-Softmax NaN**: 安定な `jax.nn.log_softmax` で生徒・教師間 KL を定式化。
4. **Host OOM / I/O ハング**: 短期診断時はチェックポイントを停止。

```python
# 10step 診断用 最小実行設定スニペット
diag_config = {
    "optimizer": "adamw",
    "weight_lr": 2e-5,
    "scale_lr": 1e-5,
    "temperature": 1.5,
    "save_every": 0,
    "devices": 1,
}
```
