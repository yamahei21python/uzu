# uzu用 Speculator 自作パイプライン計画（確定版）

- 日付: 2026-11-06（改訂: 調査結果 v3 に合わせ、R0 の測定拡張とゲート G0、判断軸の訂正、隠れ状態の保存方式、初号機の見積もりの対応づけを反映。あわせて検収で確定した uzu タグ対応を反映）
- 位置づけ: 本書が計画の正式版。根拠は調査結果（FINAL_REPORT.md v3）。旧計画書2本（PLAN_DFLASH_HERETIC.md、PLAN_SPECULATOR_PIPELINE.md）は履歴
- 前提（本人の方針）: 今後も uzu で使いたいモデルが出てくる。DFlash／Weaver をモデルごとに作り直すのではなく、**モデルを差し替えれば使い回せる仕組み**として持つ
- 最終形: 実行環境は uzu。出力は Mirai 公式パッケージと同じレイアウトの束（本体＋`speculator/`＋マニフェスト）
- 進め方の原則: 手がかりなしに自分用モデルへ直行しない。まず既存と同等の束を再現して工程を証明し、それから自分用モデルに適用する

## 設計原則

1. **モデル差し替えは「設定＋計算」で済ませ、モデルごとにはコードを書かない。** モデルごとに変わるのは config の値（hidden 次元、層数、mask トークン、対象層）と学習計算だけ（系列ごとの適合作業――ModelSpec 登録や生成器など、仕組み側のコードはありうる）
2. **アーキテクチャ系列ごとに一度だけ適合作業**をする（最初の系列は Qwen3.5 GDN ハイブリッド）。同系列の別モデルは原則 config のみ
3. **全工程を再開可能に**: データ生成・隠れ状態計算・学習は小さい単位で保存し、中断・再開・部分再実行ができる形にする（チェックポイント＋冪等な上書き、小さなコミット単位）
4. **測定までを工程に含める**: uzu 実機での受理率・実効速度を測り、結果を束のマニフェストに記録して初めて「完成」
5. 出力形式は Mirai 公式束に揃え、uzu 側の前提（shapes.json 必須、SpeculatorModel 形式）から逆算する

## フェーズ構成

全体は「紙上判定フェーズ（投資前の分岐解消）→ 再現フェーズ（工程の証明。冒頭の R0 で判断ゲート G0）→ パイロット（自分用モデルへの適用）→ 使い回し運用」の4段。

### 紙上判定フェーズ（フェーズP、実機なしで分岐を潰す）

最大の分岐は実機に進む前に紙上で大半が判定できる。R0〜R2 へ投資する前にここを済ませる。

- **P1 uzu ローダーのソース判定 ―― 完了（2026-11-06、Claude確認）**: `dflash_tfm.rs`（コミット 8962d3e）で、Weaver は Option 保持、構築方法は Argmax／Weaver の2値と判明。**DFlash 単体は設計上動作する**ため、Weaver は前提ではなく任意の上乗せ。R1 の焦点は「可否」から「実地の動作確認」に下がった。注記: このコミットが uzu のタグ 0.6.17 そのものであることは git のタグ参照で確認済み（残るのは実機バイナリの版表示の照合のみで、R0a の開始時に行う）
- **P2 Weaver 学習コードの調査 ―― 未実施**: SpecForge 等に Weaver の学習があるかを、アングラ委託＋Claude 検収で確定する。P2 で分かるのは「作れるか、どれだけ自作が要るか」で、「作る価値があるか」は R0b の実測で決める。S3 の工数（A1／A2′ の項目2、14〜22h）の見積もりが、ここで確定する

### 再現フェーズ（対象: 公式 Qwen3.5-9B）

正解の束（Mirai の Qwen3.5-9B-M／L）が存在する唯一のモデルで工程を通し、答え合わせをする。

- **R0 基準測定と判断ゲート G0**: 学習も梱包もせず、既存の束と heretic 版だけで、後続の投資判断に要る数値を先に取る
  - **R0a**: Mirai 束を uzu でそのまま（Weaver 方式）動かし、受理長と実効 tok/s を測る。同条件で **投機なしの自己回帰 tok/s も測る**（倍率の基準。判断軸はこの実測値を使う）。実機の uzu 版でソース（P1）を照合する。uzu の受理長が SGLang の受理長と同じ定義かを確認して記録する。測定ハーネス（S5）の最初の仕事を兼ねる
  - **R0b**: 同じ束で shapes.json の木の構築方法を Argmax に切り替え（Weaver 重みは使わない）、同条件で測る。**Weaver の上乗せ効果の実測**になる。shapes.json の tree_budget 等は Weaver 用の値のため、Argmax にも最適とは限らない。差は幅つきで読む
  - **R0c（A0 の前倒し）**: S0 の最小版（heretic 版の ModelSpec 登録と本体変換）だけを済ませ、Mirai 束の speculator をそのまま heretic 版に載せて測る。同一アーキテクチャなので受理が多少出る可能性があり、lossless は検証器が保証するため、失敗しても出力は壊れず遅いだけ。学習ゼロの最安基準線になる。測定は束の既定方式（Weaver）で行い、Argmax 版が要れば R0b と同じ切替を heretic でも取る（調査結果 §6 の A0 は、この Argmax 版を工数の基準にしている）
  - **G0（判断ゲート）**: R0 の結果で次を判断する（数値の基準は後述の判断軸）。(1) R0b の Argmax が判断軸に近く、R0a との差（Weaver の上乗せ）が小さい → S3（Weaver 学習）を凍結する。(2) R0c の A0 が判断軸を満たす → heretic 版の学習は見送れる。ただし「使い回せる仕組みを持つ」という本人方針に基づいて R1 以降を続けるかは別判断で、本人が決める。(3) どちらも届かない → R1 以降へ進む
- **R1 梱包の再現（学習なし）**: z-lab 公式 DFlash を `lalamo speculator convert` ＋自作 shapes.json で束にし、uzu で起動・測定する
  - ここで潰れる未確認: 変換・梱包の手順、**DFlash 単体で uzu が受理するか**の実地確認（Weaver なしの config を convert が出せるか、Argmax の指定表記を含む）、shapes.json 生成の勘所
- **R2 学習の再現**: SpecForge で公式 Qwen3.5-9B 用 DFlash を学習し、束にして測る。2段に分ける:
  - **R2a 工程の貫通**（小規模学習）: 学習が回る → convert が通る → uzu が起動する → 受理長が下限（目安 2.0、Claude提案値。R0a で受理長の定義を確認してから確定）を超える、までを見る。公式版（約800K 学習）に小規模で並ぶことは求めない
  - **R2b 規模の伸び**: データ規模を上げたとき受理長と実効速度がどう伸びるかを見て、本番規模と費用の見通しを立てる。隠れ状態の保存方式（S1）の容量・時間の実測もここで行う
  - ここで潰れる未確認: **SpecForge の 9B GDN での隠れ状態取得**（同3）、**SpecForge 出力の convert 取り込み可否**（同4）
- **同等の判定基準**: (a) uzu で起動し投機が有効に動く、(b) lossless が許容付きで保たれる（後述）、(c) R2a では受理長が下限超え、R2b／完成判定では実効 tok/s が判断軸（後述の最低ライン）を満たす、(d) 束のレイアウトとマニフェストが公式束と同形
- **lossless の定義（許容付き）**: バイト一致は求めない。4bit 量子化では検証パスと通常デコードでカーネルが異なり、正しく動いていても数値差で出力が分岐しうるため、greedy でのトークン一致率（目安 99% 以上）または logit 差の上限で判定する
- 分岐: P1 で DFlash 単体は設計上可と判明したため、R1 で起動しない場合は仕様ではなく不具合・手順の問題として切り分ける。Weaver が必須になるのは、Argmax 方式の受理が判断軸に届かず、R0b で Weaver の上乗せが十分大きいと分かった場合に限る

### パイプライン本体（S0〜S6）

再現フェーズで各工程の実物を作り、パイロット以降はこれを使い回す。

| 工程 | 内容 | モデルごとの差分 |
|---|---|---|
| S0 取り込み・登録 | **着手前の入口確認（対応ゲート）を必ず先に行う**: (1) lalamo の ModelRegistry にその系列の登録があるか、無ければ ModelSpec 登録だけで足りるか（既存の HF config 実装に適合するか）、(2) uzu 側にそのモデルの構成部品（プリミティブ）が揃っているか――uzu はモデル系列ごとの実装ではなく config 駆動で、token mixer 等の部品の組み合わせで動く（例: Qwen3.5 の GDN は token_mixer の delta_net として実装済みで、Metal カーネルも gdn 配下にある。2026-11-06 にローカルの uzu ソースで確認）。新しい部品を要するモデルだけがここに引っかかる、(3) SpecForge 側でドラフト config が起こせるか。欠けが (1) の登録だけなら想定内の軽作業として進める。(2) の部品が欠ける系列は原則として入口で止める（uzu 側に新しいプリミティブを実装するのは本計画の対象外）。通過後に、HF のモデル ID＋リビジョンを固定し、lalamo へ ModelSpec 登録、本体を uzu 形式へ変換。層数・hidden 次元・語彙・mask トークンを自動抽出 | 系列ごとに登録作業。同系列内は自動抽出のみ |
| S1 データ工場 | プロンプト資産はモデル共通で版管理（一般ベース＋§4 のドメイン系）。モデル別に、対象本人による応答生成と隠れ状態の用意。規模は 10K → 100K → 本格と段階拡大し、受理の伸びで止めどころを決める。**応答生成の条件（thinking の有無、温度、最大長）は受理率に効くため、データの版情報として必ず記録する**。**隠れ状態の方式**: 保存して使うオフライン方式は、容量が「層数×hidden 次元×2 byte×総トークン数」で増える（hidden 4096・8層で、平均1,000トークンの1万件が約0.7TB、10万件が約6.5TB。調査結果 §4）。既定は、1万件級まではオフライン、10万件以上はオンライン方式（学習中に対象モデルで再計算）とし、境界は R2b の実測で確定する。保存を絞る工夫（対象層数、系列長の上限）は、見積もりの後に判断 | 生成と計算のみ（コード差分なし） |
| S2 DFlash 学習 | SpecForge（SGLang 系の学習基盤。採用理由: 出来合いの基盤と実績あるレシピで開発時間を削り、受理率の再現性を取るため。uzu は推論専用で、SGLang は学習の作業場として Modal 上でのみ使う。本人の判断で存続を確定、2026-11-06）。モデル別 config は S0 の抽出値から自動生成（target_layer_ids は論文方式の5層均等／Mirai 束方式の8層を選択可、block 16）。既定値は論文A.1（6エポック、AdamW、lr 6e-4、系列長3072、アンカー512、γ=7）。同系列の公開品があれば微調整開始も可。training_state を保存して再開可能に。オフライン／オンラインは S1 の方式に合わせる。計算は Modal | config の値と計算のみ |
| S3 Weaver 学習 | 入出力の契約は Mirai 束の weaver_config 形式に固定し、差し込み口を先に作る。学習コードの公開状況（P2）と上乗せ効果（R0b）が出るまでは凍結し、v1 は DFlash のみで束を作る | 学習計算のみ（予定） |
| S4 変換・梱包 | `lalamo speculator convert` で SpeculatorModel 形式へ。shapes.json は生成器で作る（Mirai 束の実物が雛形: default とチップ別プロファイル、tree_budget／max_tree_depth／rounds／expand_per_round／expand_width）。束にマニフェスト（対象モデル ID＋リビジョン、データ版と生成条件、学習 config、S5 の測定要約、**lalamo／uzu のバージョン**）を付ける。上流の仕様変更が速い（NGram 削除の例）ため、バージョン固定は必須 | 自動生成のみ |
| S5 検証 | uzu 実機で単体（自己回帰）と投機ありを同条件で測定し、受理長と実効 tok/s を言語別・ドメイン別に出す。lossless は許容付き定義（greedy 一致率等）でチェック。**学習時の隠れ状態は BF16 の対象モデルから取る一方、推論は 4bit（M）／8bit（L）の量子化版になるため、この分布ずれを見て受理を量子化別にも測る**。結果をマニフェストに記録し、基準未達の束は未完成として区別 | 測定のみ（自動） |
| S6 カタログ | 完成した束を名前規則（対象モデル名＋日付＋データ版）で保管し、選んで載せ替えられるようにする。保管先は当面ローカル、必要に応じて HF プライベート。**開始は「ディレクトリ＋命名規則」の簡易版で足り、本格的なカタログ化は M3（2モデル目）まで後回しでよい** | ― |

### パイロット（対象: heretic版 Qwen3.5-9B）

再現フェーズ通過後に、証明済みの工程をそのまま適用する。heretic版固有の作業は S0 の登録と、受理率の転移の確認だけ。

1. **流用測定（先行、2本立て）**:
   - (a) Modal＋SGLang で z-lab 公式 DFlash の受理率を3対象で測る ―― 公式 Qwen3.5-9B（基準。論文 Table 11 の受理長は課題別に 5.5〜7.9。**本計画の用途は対話・RP なので、比較の目安は MT-Bench に近い下側の 5.5**。日本語は別途測る）／Jackrong 蒸留版／heretic版。どこで受理が落ちるかで、微調整（A1+）か新規学習（A3／A2′）かを決める。uzu 経由で測らない（登録と shapes.json が先行してしまうため）。これは GPU＋SGLang の値で、uzu の実効速度とは直接比較しない
   - (b) **A0 測定**: R0c で Mirai 束を載せた値が取れている。ここでは、R1 で作った z-lab DFlash の束を heretic 版に載せ替えた値（A0′）を追加で取る。A0 系の値がそのまま「自作する価値」の下限比較になる
2. **S0〜S2 の適用**: 登録（R0c の最小版を拡充）→ データ（スターターミックスを核に段階拡大、応答は heretic 本人が生成）→ SpecForge 学習（初期値は流用測定の結果で、z-lab 品かゼロからかを選択）
3. **S4〜S6 の適用**: 梱包 → uzu 実機で検証 → カタログ登録


## 判断軸（先に決める中止ライン）

- **最低ライン（提案値、本人が確定する）**: 自分の用途（対話／RP 中心）での実効 tok/s が、対象モデル単体（uzu、投機なし）比で **1.5倍以上** を完成の条件とする。基準となる uzu 素の自己回帰 tok/s は R0a で測る
- **訂正（前版の誤り）**: 前版は「Mirai-M は素でも M5 で 92 tok/s 級」と書いたが、92.1 tok/s は投機ありの値で、比較先も llama.cpp の素のデコードだった（調査結果 §1）。uzu 素の値は未測定のため、この数値を判断の根拠に使わない
- 倍率に加えて、使い心地に必要な**絶対 tok/s も本人が決める**（倍率が足りていても、素の速度が既に十分速ければ投資の価値は下がる）
- 使い方: G0、R2b、M2 の判定に使う。A0（学習ゼロ）で既にラインに届くなら自作は見送る。逆に A3／A2′ まで進んでも届かない見通しなら、M1 の時点で中止できる
- 数値は提案であり、用途の速度要求が変われば差し替える。重要なのは「着手前に決まっている」こと

## コスト構造（暫定）

- **再現フェーズ**: R0 は測定のみ（作業時間は半日〜1日級の見込みで、項目表には無い Claude の見立て）。R1 は学習なしで数時間級＋実機作業。R2 は小規模学習の計算費（Modal、数ドル〜十数ドル級）＋工程構築の作業時間。ここが仕組み側の投資の大半
- **計算費の内訳（DFlash 学習本体を含む、暫定・要実測）**: 従来の試算（1,000件の trace＋Weaver 学習で約$0.76、10万件で約$76）は「生成＋隠れ状態取得」側だけの線形延長で、DFlash の学習計算は入っていない。パイロット規模（10万件級、6エポック想定）の概算は、取得側 約$70〜80 に学習側（ドラフトは小さく、数十 GPU 時間級として A100 換算で約$50〜250）を加え、**合計 $100〜400 の幅**と置く。この幅はオフライン／オンラインの区別を置いておらず、オンライン方式は各エポックの対象モデル順伝播分が、オフライン方式は TB 級ストレージの費用・転送が上振れ要因になる。規模を論文級（約800K×6エポック）に上げれば $1,000 超もありうるため、R2b の実測で単価（1件あたり・1エポックあたり）を確定してから本格規模の予算を決める
- **パイロット（初号機）**: v1 は DFlash のみ（S3 凍結）で作るため、見積もりの土台は調査の **Route A3（28〜54h）**。Weaver を足す場合は Route A2′（42〜76h）。学習ゼロで済む場合は Route A0（16〜32h）。再現フェーズで未知数が潰れている分、実作業は下限側に寄る見込みだが、これは未検証。なお再現フェーズと初号機は工程の一部が重なり、再現フェーズの作業時間を別に足した総量は未見積もり
- **2モデル目以降（同系列）**: S0 の確認＋S1／S2 の計算＋S5 の判定が中心で、作業は数時間〜十数時間級＋計算費（規模依存で数十ドル級〜）に縮む、というのが本計画の狙い。M3 で実測して裏付ける
- **新系列の追加**: 系列ごとに S0 の登録と SpecForge config の適合作業が発生する（モデルごとではない）

## マイルストーン

- **M-P** 紙上判定完了: P1（済み: DFlash 単体は設計上可）と P2（Weaver 学習コードの有無）で、投資前の分岐が解消している
- **G0** 判断ゲート（R0 完了時）: R0a〜R0c の実測で、Weaver の要否、heretic 版の学習の要否、再現フェーズ以降を続けるかの本人判断を行う
- **M0** 再現フェーズ完了: R0〜R2 を通し、判定基準 (a)〜(d) で「既存と同等の束が作れる」ことを確認
- **M1** パイロット前半: 流用測定の結果が出て、微調整か新規学習かの分岐が決まる
- **M2** パイロット完了: heretic版の束が uzu で動き、S5 の測定で実効速度の改善が確認され、マニフェスト付きでカタログ登録される
- **M3** 使い回しの証明: 同系列の2モデル目を通し、「設定＋計算だけ」で束が作れることと、2モデル目の実コストを実測する
- **M4** Weaver の最終判断: P2（学習コードの有無）と R0b（上乗せ効果）の両方を踏まえ、S3 を実装するか、DFlash のみで運用を続けるか決める

## 役割分担

- 実機作業（uzu／lalamo の実行、Modal での学習と測定）: 本人
- **計算資源の使い分け（Modal の併用）**: 対象マシンは MacBook Air M3（統合メモリ 16GB、ファンレス）で、メモリ量と持続負荷に制約がある。ただし **Modal にも利用上限（無料枠等）があるため、原則は「小さいものは M3 で動かし、Modal は大きいものだけに使う」**。M3 で短時間に終わる生成・変換・小規模な測定は実機で済ませる。Modal を使うのは、実機のメモリや時間では回らない規模のもの、および GPU が要る SGLang での受理率の先行測定や本格学習など実機では非現実的なものに限る（パイロット手順1(a) と S2 が該当）。uzu の実効速度と受理の最終測定はチップと量子化に依存するため、いずれにせよ Mac 実機で測る。測定はメモリの余裕から M（4bit）版を先行させ、L（8bit）版は後にする
- 計画・調査・検収（本書と FINAL_REPORT の維持、委託調査の取りまとめ）: Claude
- 大規模な追加調査（Weaver 学習コード等）: アングラへ委託し、Claude が出典を再確認して確定する
