# Kaggle CPU カーネルの上限（2026-11-07 調査）

## 公式・一次情報

| 項目 | 値 | 出所 |
|---|---|---|
| 1 セッションの実行時間 | **12 時間**（CPU / GPU）。TPU は 9 時間 | Kaggle Notebooks ドキュメント / Kaggle 公式告知（9h → 12h に延長） |
| CPU の週次クォータ | **無し**（GPU は 30h/週、TPU は 20h/週） | ドキュメント / アカウントの Quota 表示 |
| CPU の同時セッション | **5 本**（古い情報では 10 本） | Kaggle フォーラム「Maximum batch CPU session count of 5 reached」 |
| GPU の同時セッション | 2 本 | 同上・運用実績 |
| CPU スペック | 4 vCPU / 30GB RAM | ドキュメント |
| `/kaggle/working` | 20GB | ドキュメント |
| 出力（commit の成果物） | 20GB まで | ドキュメント |
| idle 停止 | 操作なしで一定時間（20〜60 分）で停止 | ドキュメント・運用 |

**注意**: 同時セッション数は 5 と 10 の両方の情報がある。2024 年以降のフォーラム報告は **5**。
確実に言えるのは「GPU より多い」こと。3〜4 本を同時に走らせる運用は安全側。

## 我々の使い方への含意

| 制約 | 影響 | 対策 |
|---|---|---|
| 12h/セッション | 6 条件（1 条件 40〜90 分）は収まる | カーネル A/B に分割済み。`--shard` でも可 |
| CPU クォータ無し | 何本回しても課金・消費なし | 0.8B は CPU が本線。T4 は BF16 不可 |
| 同時 5 本（推定） | owner 2 + Muse 2 = 4 で余裕 | 5 本目を立てない |
| RAM 30GB | 0.8B float32（3.2GB）+ INT4（0.55GB）+ JAX で余裕 | 4B は FP32 16GB で溢れる → CPU 不可 |
| working 20GB | 条件ごとに `calibration.npz`（1.4GB）を消している | 消さないと 10 条件で溢れる。`run_lane` は変換後に削除する |
| 出力 20GB | 結果 JSON だけなら数百 KB | `calibration.npz` を上げない |

## 実測（こちら）

| 項目 | 値 |
|---|---|
| M3 10 コアでの 1 条件（mix65、float32） | calibration 約 10 分 / convert 626 秒 / eval 各 11 分 = 約 40 分 |
| Kaggle 4 vCPU の見込み | M3 の 1.5〜2 倍 = **60〜80 分/条件** |
| カーネル A（6 条件） | 6〜8 時間 |
| カーネル B（4 条件） | 4〜5.5 時間 |

## 運用ルール

1. CPU カーネルは **GPU を付けない**（`enable_gpu: false`）。付けない限り GPU クォータを消費しない
2. 1 カーネル 12h を超えそうなら `--shard` で分ける。`result.json` がある条件は再実行で skip
3. `/kaggle/working` を圧迫しないよう、`calibration.npz` は変換後に削除（`run_lane` が実施）
4. 同時は 4 本まで（owner 2 + Muse 2）。5 本目は立てない
5. 結果は `kaggle kernels output` で回収し、`<user>/uzu-results` に上げる

## 未確認（推測で運用しない）

- 同時セッションの正確な上限（5 か 10 か）
- CPU カーネルの idle 停止までの正確な分数
- commit モードで 12h を超えた場合の挙動（打ち切り or 失敗）
