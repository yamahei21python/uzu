# Weaver（木の提案器）の検討メモ（2026-11-09）

## 何か

公式 speculator の後半。DFlash が出す**周辺分布（トークンごとの独立予測）**を、
**自己回帰的に木へ展開**する小さなアダプタ。

論文: *Trees from Marginals: Autoregressive drafting with factorized priors*
（arXiv 2607.06763）

| 項目 | 値 |
|---|---|
| パラメータ | **56.7M**（本体の 0.6%） |
| 出力 | **top-512 候補上の残差 logits**（フル語彙は出さない） |
| 層 | 1 層 / 2048 dim / 16 heads |
| 木 | max_depth 15 / rounds 8 / expand 4 / candidate_pool 512 |
| 効果（27B, B200） | AR 89.9 → DFlash 315.0（3.5x）→ **TfM 392.8（4.37x）** |
| 最適 budget | **64** |

我々の 9B speculator の config はこれと一致している（`candidates_pool_size: 512`、
`max_depth: 15`、`rounds: 8`、`expand_per_round: 4`）。**同じ設計を学習すればよい。**

## なぜ「やすい」のか

| 項目 | Weaver | draft（DFlash） |
|---|---|---|
| パラメータ | 57M | 377M |
| 出力 | 512 候補の残差 | フル語彙 248k |
| 学習信号 | 次トークン（教師ありのみ） | 同 |
| 強化学習 | **不要** | 不要 |

フル語彙 softmax を 512 に絞るので、計算もメモリも小さい。
**受理・棄却の信号も要らない**（実現系列を教師にすればよい）。

## 難所はデータ

1. draft を走らせ、**トークンごとの top-512 候補**を保存
2. 実現した系列（我々の 9B の生成結果）を正解として用意
3. Weaver は「実現トークンを条件に次の候補の残差」を交差エントロピーで学習

保存量の見積もり:

| 候補数 | 1 トークン | 10M トークン |
|---|---:|---:|
| 512（id+logit） | 4KB | 40GB |
| 512（id のみ） | 2KB | 20GB |
| **64（id のみ）** | **256B** | **2.5GB** |

→ **top-64 に削る**のが現実的（パイロットはこれで十分）。

## どこで回すか

| 段階 | 置き場所 | 根拠 |
|---|---|---|
| **データ生成（9B 推論 + キャッシュ）** | **Modal A100** | T4 だと 10M トークンで 60〜90 時間。Kaggle の週次 30h を超える |
| **Weaver 学習（57M）** | **Kaggle T4×2 で可** | 小モデル。1 epoch 1〜2 時間 |
| **検証（uzu で τ / t/s）** | ローカル Mac | Apple silicon 専用 |

T4 での実測目安（`uzu-t4-probe`）: fp16 1.35 TFLOP/s。9B 生成はバッチで 30〜50 t/s。

## パイロット（Kaggle だけで判定する場合）

| 項目 | 値 |
|---|---|
| データ | 2M トークン |
| 候補 | top-64 |
| 生成 | T4×2 で 12〜18 時間（1 セッション） |
| 学習 | 次セッションで 2〜3 時間 |
| 判定 | budget 8 / 16 / 32 / 64 で t/s と τ |

これで「Weaver が効くか」は判定できる。本番規模（10M+）は Modal。

## 順序

```
1. draft を我々の 9B で fine-tune（τ を上げる）
2. τ が伸びたら Weaver（budget 64 で +25% の見込み）
3. 両方入れて 9B の t/s を測る
```

**draft が弱いまま木を広げても意味がない。** 外れ枝が増えるだけなので、先に draft。
