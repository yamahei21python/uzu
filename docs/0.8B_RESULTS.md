# 0.8B の結果まとめ（2026-11-08）

対象: Qwen3.5-0.8B（`Qwen/Qwen3.5-0.8B`）。RHT block 32 + INT4 group 32 + YAQA。
別段の注記がない限り **dedup コーパス / 100 chunks / max_tokens 128**。

## 0. 指標

- **BPC の相対差**（同じ言語内）: `Δ% = (bpc_candidate / bpc_bf16 − 1) × 100`
- PPL の比ではない。PPL の絶対値・比は言語間で比較しない
- BF16 baseline: EN 35.376〜35.386 / JA 43.421〜43.430（レーン間で 0.02〜0.06% の差）

## 1. 変換だけ（校正なし）

| 条件 | EN | JA | chunks |
|---|---:|---:|---:|
| RTN（mixed コーパス扱いなし） | 3.01% | 4.01% | 100 |
| RTN（旧・50 chunks） | 2.81% | 4.15% | 50 |

## 2. 校正コーパス（s32 / q128 / d1e-3 / uniform4）

| コーパス | EN | JA |
|---|---:|---:|
| enonly | 3.02% | **9.67%** |
| mix35 | 3.36% | 3.43% |
| mixed50 | 3.36% | 3.70% |
| mix65 | 3.81% | 3.52% |
| jaonly | 7.13% | 3.71% |

- enonly は JA が壊滅（校正分布のミスマッチ）
- mixed50 / mix35 が実用域。混合比 50 vs 65 の差は seed 幅内で**有意でない**

## 3. damping（s32 / q128 / uniform4）

| damping | mixed50 EN | mixed50 JA | enonly EN | enonly JA |
|---:|---:|---:|---:|---:|
| 1e-3 | 3.36% | 3.70% | 3.02% | 9.67% |
| 1e-2 | 2.16% | 2.73% | 1.91% | 6.52% |
| 1e-1 | 1.99% | 2.26% | 2.26% | 4.20% |
| **1e0** | **1.58%** | **2.04%** | **1.70%** | **3.15%** |

- s32 では **1e0 が最良**まで改善
- s64 / q512 では 1e0 は悪化（1.95 / 2.22）。**samples が多いほど最適 damping は小さくなる**
- 解釈: damping は「ヘッセ推定のノイズ補正」。samples と同じ方向のレバー

## 4. samples × max_tokens（damping 1e-2 / uniform4）

| 条件 | 総トークン | EN | JA | デバイス |
|---|---:|---:|---:|---|
| s16 q128 | 2k | 2.80% | 3.82% | CPU |
| s16 q256 | 4k | 3.01% | 4.33% | CPU |
| s16 q512 | 8k | 1.97% | 2.52% | GPU |
| s32 q128 | 4k | 2.16% | 2.73% | CPU |
| s32 q256 | 8k | 1.60% | 2.76% | CPU |
| s32 q512 | 16k | 1.99% | 2.26% | GPU |
| s64 q128 | 8k | 2.44% | 2.93% | CPU |
| s64 q256 | 16k | 1.86% | 2.42% | CPU/GPU |
| s64 q512 | 32k | 1.59% | 1.98% | GPU |
| s128 q512 | 65k | 1.42% | 1.53% | GPU |

- samples が効く（s16→s64 で改善）。seq も効くが、samples の方が支配的
- 32k → 65k の改善は seed 幅内で**有意でない**。校正時間は 2 倍
- q1024 は calibration が失敗（code 1、原因未特定）

## 5. 8bit 配分（s32 / q128 / d1e-1）

| 配分 | EN | JA | サイズ増 |
|---|---:|---:|---:|
| uniform4 | 1.99% | 2.26% | — |
| down + out_proj | 1.39% | 1.70% | +0.06GB |
| **down + out + qkvg + out_projection（wide8）** | **1.13%** | **1.24%** | +0.08GB |

- down/out の寄与は両言語で seed 幅超え
- **wide8 の追加分は JA で一貫して有意、EN は有意でない**

wide8 の 3 seed（s32 / q128 / d1e-1 / mixed50、emb4）:

| seed | EN | JA |
|---|---:|---:|
| 0（既定） | +1.13% | +1.24% |
| 1 | +0.69% | +1.22% |
| 2 | +1.32% | +1.39% |
| 平均 | **+1.05%** | **+1.28%** |

- JA は 3 seed とも down-out8（+1.70%）を明確に下回る → **wide8 の JA 優位は確定**
- EN は 3 seed とも down-out8 以下だが差は薄い。seed2 は基準線 1.3% を 0.02pp だけ超える
- EN で wide8 を主張するには seed をもう 2〜3 本必要（現在の seed 幅 0.44pp > 平均差 0.34pp）

damping を 1.0 まで上げた場合（down-out8 + emb4、CUDA 不要の CPU レーン）:

| damping | EN | JA |
|---|---:|---:|
| 1e-1 | 1.39% | 1.70% |
| **1e0** | **1.27%** | **1.49%** |

- 両言語で改善方向。EN −0.12pp は seed 幅内、JA −0.21pp は seed 幅（0.25pp）と同程度
- **1e0 は無料**（速度・サイズ不変）なので採用候補。wide8 でも試す価値がある

## 6. 校正 dtype・デバイス

| 条件 | EN | JA |
|---|---:|---:|
| CPU / f32（基準） | 2.16% | 2.73% |
| **CPU / bf16** | 3.21% | 3.84%※ |
| GPU TP=2 / f32 | 2.51% | 3.04% |
| CPU / bf16（q512 s16） | 1.34% | 2.54% |
| GPU / f32（q512 s16） | 1.97% | 2.52% |

※ bf16 は d1e-3 の条件（他は d1e-2）。同条件比較は `calib-device-cpu-bf16` で実施中。

- **GPU(TP=2) の校正は CPU より 0.3pp 悪い**（JA で seed 幅超え）
- 校正は CPU で行い、GPU の校正値と混ぜない。eval はデバイス差 0.02% で混在可
- bf16 校正は CPU の q512 を可能にした（f32 は SIGKILL）

## 7. ばらつき（seed 幅）

| 設定 | EN | JA |
|---|---:|---:|
| s32 q128 d1e-3（mixed50） | 0.89pp | 0.23pp |
| **s32 q128 d1e-1（mixed50）** | **0.44pp** | **0.25pp** |
| s64 q256 d1e-2（GPU 3 seed） | 0.30pp | 0.53pp |
| **wide8 / s32 q128 d1e-1 / emb4（3 seed）** | **0.44pp** | **0.13pp** |

- **この幅以下の差は主張しない**
- 同じ条件を別レーンで回すと完全一致する（s32 q128 d1e-2: 2.16 / 2.73 が 3 回再現）

## 7.5 embedding のビット数（2026-11-08 / down-out8 + d1e-1 ベース / 100 chunks）

| embedding | EN | JA | 速度（0.8B） | サイズ |
|---|---:|---:|---:|---:|
| BF16（量子化なし） | 1.39% | 1.70% | 88 t/s | 0.92GB |
| **int8** | **1.38%** | **1.73%** | ~140 t/s | ~0.53GB |
| int4 | 2.02% | 2.56% | 143 t/s | 0.52GB |

- **emb8 は実質タダ**（量子化なしと同等の品質で、速度はほぼ int4 と同じ）
- **emb4 のコストは EN +0.64pp / JA +0.83pp**（emb8 比）
- 0.8B では embedding がパラメータの 34% を占めるため、サイズ差は小さいが速度差は大きい
- 4B/9B で emb4 を選ぶ場合の「値段」がこれで実測できた

## 9.5 QAD の効果（2026-11-08 / Muse 実行 / 50 step / 100 chunks）

最弱の student（samples 8 / damping 1e-3 / uniform 4bit）で before/after を測った。
BF16 基準は before 測定時と完全一致（EN 1.251082 / JA 3.469881）で、環境の再現性も確認済み。

| 言語 | before | after | 差 |
|---|---:|---:|---:|
| EN | +7.51% | **+6.06%** | **−1.46pp** |
| JA | +8.34% | **+7.46%** | **−0.88pp** |

- **両言語で改善**。JA より EN の伸びが大きい
- ただし絶対値は依然として悪い（最良は wide8 の 1.13 / 1.24）
- 対象が「最弱の較正」なので、**弱い較正を QAD が部分的に補う**という見方と整合する
- 強い較正（wide8 + d1e-1）に乗せたときに同じ幅が出るかは別問題。逓減が予想される
  → `uzu-qad-best`（CPU）で wide8 + emb4 の student に 50 step を実行中

### 生成物

Muse が HF に 2 形式で保存している。

| 名前 | 形式 | 用途 |
|---|---|---|
| `qad-50step-run-fixed` | flat（uzu 向け） | uzu で起動する |
| `qad-50step-run-nested` | nested（lalamo 向け） | eval |

## 10. 結論

1. 校正は **mixed50（または mix35）+ samples 多め + damping 適正**が効く
2. **8bit を出力側に寄せる**のが最も安い改善（+0.08GB で 1.85→1.13%）
3. samples と damping は代替関係。samples を増やすなら damping は下げる
4. 0.8B は CPU で完結する。GPU は q512 など CPU で不可能な条件のみ
5. 3% 前後の差を議論するときは seed 3 本（EN 0.4〜0.9pp / JA 0.25〜0.53pp）が必須

## 11. TPS: 公式モデルとの比較（2026-11-08 実測）

MacBook Air M3 16GB、`cli bench`（UI 無し、tokens 512 × 2 runs、back-to-back 測定）。

| モデル | サイズ（実行時） | Generate |
|---|---:|---:|
| 公式 `alibaba:qwen3.5:0.8b:mirai:mirai-m:4` | 0.521GB | **142.9 t/s** |
| **我々の変換（RTN + embedding 4bit）** | **0.521GB** | **143.0 t/s** |
| 我々の変換（RTN、embedding は BF16 のまま） | 0.92GB | 87.9 t/s |

- **embedding を量子化するだけで公式と同等**になる（サイズ・速度とも一致）
- 校正（YAQA）・damping・8bit 配分は**速度にほぼ影響しない**（バイト数が同じため）
- 測定は熱の影響で ±5% 動く。公式→我々→公式の順で回すと 132 / 143 / 143 と収束した

**速度の要件は2つだけ**: lalamo/uzu 形式への変換、embedding/readout の量子化。
品質の要件（YAQA / damping / 8bit）は速度と独立。


## 11.2 品質: 公式 0.8B-M vs 我々の wide8（2026-11-08 実測）

同じ BF16・同じコーパス・同じ 100 chunks / 128 tokens / float32 で測った ΔBPC。

| モデル | EN | JA | サイズ |
|---|---:|---:|---:|
| **公式 `Qwen3.5-0.8B-M`**（4bit g32 + emb 量子化 + QAD） | **+1.21%** | **+3.83%** | 0.409GB |
| **我々 wide8 + d1e-1 + emb4** | **+1.13%** | **+1.24%** | 0.44GB |
| 我々 down-out8 + d1e0 + emb4 | +1.27% | +1.49% | 0.43GB |
| 我々 uniform4 + d1e-1 + emb4 | +1.99% | +2.26% | 0.44GB |

- **EN は互角**（0.08pp 差、seed 幅 0.44pp より小さい）
- **JA は我々が 2.6pp 良い**（公式 +3.83% vs 我々 +1.24%）。seed 幅 0.25pp の 10 倍
- 公式は **英語では強いが日本語で大きく崩れる**。校正・QAD のデータが英語中心と推測される
- 我々の mixed50（EN/JA 混合）校正が JA で効いている

**「公式より少し遅いが品質は良い」は JA について成立。EN は同等。**

注意: 我々の wide8 は asymmetric int8（§11.5）。symmetric 再測定で数値は動くが、
JA の 2.6pp 差は seed 幅の 10 倍なので順序は覆らない見込み。


## 11.3 速度: symmetric int8 の実測（2026-11-08 / M3 16GB / tokens 512 × 2）

| モデル | 実行時メモリ | Generate | 公式比 |
|---|---:|---:|---:|
| **公式 0.8B-M** | 0.521GB | **142.9 t/s** | — |
| uniform4 + emb4 | 0.521GB | **146.1 ± 1.2 t/s** | +2% |
| down-out8 + emb4 | 0.566GB | **128.4 ± 3.8 t/s** | **−10%** |
| wide8 + emb4 | 0.597GB | **124.4 ± 0.7 t/s** | **−13%** |

- 8bit 配分のコストは**ほぼバイト数に比例**（down-out +8.6% / wide +14.6%）
- 以前の「−12%」推定は wide8 でほぼ当たり（実測 −13%）
- **JA で 2.6pp 品質が上がる代償が −13% の速度**。0.8B では妥当な取引

## 11.5 注意: 8bit 配分は asymmetric で測っていた（2026-11-08 判明）

本ドキュメントの wide8 / down-out8 の数値は **asymmetric int8**（zero point あり）の測定値。

uzu は zero-point dequant を 4bit 用にしかコンパイルしないため
（`gemm.metal`: `B_PROLOGUE != ScaleZeroPointDequant || BITS == 4`）、
この構成のモデルは **uzu で起動できなかった**。`9e471128` で変換器が
8bit を symmetric で出すよう修正した（`--symmetric-bits` 既定 8）。

- 品質への影響: symmetric は absmax 正規化なので、外れ値がある層でわずかに悪化しうる
- 速度への影響: 未実測（動かなかったため）。W8 は `Tile8x32x128` でカーネルが 4bit と別物
- 以降の wide8 / down-out8 の数値は **symmetric で再測定する**
